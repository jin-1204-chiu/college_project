## 🔍 API 測試核心項目
API 測試主要確保系統間溝通的穩定性，報告中列出了五大檢查重點：
* **HTTP Status Code**：確認請求回覆的狀態碼（如 200 OK、404 Not Found、500 伺服器錯誤等）[cite: 62, 70]。
* **Response Body & Schema**：驗證回傳的資料與結構是否符合預期，避免因格式錯誤（如預期數字卻回傳字串）導致前端崩潰[cite: 62]。
* **Performance（效能）**：測試回應時間與負載能力，模擬多人同時使用的情境[cite: 62]。
* **Security（安全性）**：檢查 Header 是否包含敏感資訊，以及權限控管是否正確[cite: 62]。
* **Error Handling（錯誤處理）**：確認錯誤發生時，系統是回傳簡潔訊息，還是洩漏了伺服器路徑等敏感程式碼報錯[cite: 62]。

## 🛠️ Postman 平台優勢與功能
相較於使用傳統的命令提示字元（cmd）與 `curl` 指令，Postman 提供了以下優勢與進階功能：
* **直覺的 GUI 與轉換功能**：支援 Request 保存、Token 繼承，並能將 API 請求快速轉換為多種程式語言腳本（如 Python、R、Ruby 等）[cite: 63, 64]。
* **Mock Server（模擬伺服器）**：在前後端分離的架構下，可模擬測試環境，避免開發進度互相阻塞，實現平行開發[cite: 67]。
* **Monitors（監控）**：可設定排程（例如每 5 分鐘執行一次），若 API 回應狀態碼異常，系統會自動發送 Email 通知[cite: 67]。

## 💻 實機自動化測試展示
報告中使用了自建的 Node.js/Express 測試伺服器，展示了多種 HTTP 請求與自動化應用：
* **HTTP Methods 測試**：展示了 GET（取得資料）、POST（新增/登入）、PUT（全部更新）、PATCH（部分更新）、DELETE（刪除）、HEAD（僅查看 Header 節省流量）與 OPTIONS（查看支援的 Method）的實際操作[cite: 71, 72, 80, 81, 82, 83, 84]。
* **環境變數與腳本攔截**：利用環境變數儲存 Token，並展示了當後端發生 Bug 時，Postman 如何有效攔截並呈現錯誤（Status 500）[cite: 79, 85]。
* **資料驅動測試 (Data-Driven Testing)**：利用 Postman 內建的 "Runner" 功能，匯入 CSV 檔案進行批量的登入測試驗證[cite: 86, 102]。
* **Newman 整合**：將測試 Collection 導出為 JSON 檔，透過 Newman 工具於終端機執行自動化測試腳本[cite: 87]。

## ⚖️ Postman 與 Selenium 的測試定位比較
報告最終對比了 Postman 與自動化 UI 測試工具 Selenium 的差異與適用場景：

| 比較項目 | Postman | Selenium |
| :--- | :--- | :--- |
| **測試階段** | 子系統測試 (Sub-system testing)[cite: 98, 103] | 系統測試 (System testing)[cite: 98, 103] |
| **測試對象** | API 協定與後端通訊[cite: 103] | Web UI 畫面與功能互動[cite: 97, 103] |
| **執行效能** | 極快（跳過瀏覽器渲染，直接封裝 HTTP 封包通訊）[cite: 100, 103] | 較慢（需啟動瀏覽器實體並等待 DOM 渲染）[cite: 100, 103] |
| **報錯診斷** | 精確（基於協定層，能一眼識別路徑錯誤或無回應）[cite: 101, 103] | 較難（通常報錯為元素找不到或逾時，難以第一時間判斷根本原因）[cite: 101, 103] |
| **資料驅動** | 自動（內建 Runner 支援匯入 CSV）[cite: 102, 103] | 手動（需自行撰寫 Python csv 讀取迴圈）[cite: 102, 103] |
| **適用場景** | 高頻率 CI/CD 自動化測試[cite: 100, 103] | 最終的端對端 (E2E) 功能自動化驗收[cite: 97, 100, 103] |

透過導入 Postman，團隊能以易懂的圖形化介面降低操作門檻，免去手動重複操作與核對的負擔，使單元、整合與回歸測試變得更加有效率且從容[cite: 89, 90]。
